> 调研时间：2026-09-30　状态：**沈阳、大连、长春均已实施（2026-10-03）；哈尔滨仍待决策**
>
> 实施口径见 7.1（沈阳）、8.1.1（大连）与 8.2.1（长春）的「实施记录」；沈阳侧代码在

> 长春侧在 `city/changchun/data_facilities.js`（由 `drunk/tools/facilities/gen_changchun_facilities.js`
> 依 `changchun_facilities.transcript.json` 生成）。
>
> 起因：上游 CentralGo（`centralgo.site/map`）上线了「出入口与设施」功能。本文核对

## 一、结论摘要

1. **设施数据值得做，成本比预期低**。沈阳、大连两市官网都刊载站内设施文字，字段规整，
   也都有现成接口；沈阳覆盖全部 159 座运营站，大连一次请求即可拿全 108 站。
2. **两市都拿不到出入口坐标**。沈阳官网干脆没有出入口信息；大连有字母、公交线路与
   周边地标、启用状态，但**没有方位、没有坐标**。要做出入口得另找来源（OSM 是候选）。
3. **纯静态站的唯一障碍是取数方式**：两市接口都是 **POST、无静态 JSON，且 CORS 只放行
   官网自身域名**（大连已实测确认），因此都需要在离线/开发阶段抓取一次落盘成静态数据。
4. **两市字段形态不同，需要一层统一 schema**：沈阳是"每站 9 行设施记录"
   （`deviceDesc` + `deviceLocationDesc`），大连是"每站 3 个平铺字段"
   （`toilet` / `rechargeMachine` / `accessibilityElevator`）。
5. **两市的官网编号映射都是现成的**：沈阳见 `data_timetable.js` 的
   `SYMTC_OFFICIAL_STATION_ID_RULES`（层级图卡片正在用），大连见
   `city/dalian/data_timetable.js` 的逐站 `siteId` 登记表。

## 二、沈阳：官网的设施数据（本次调研的核心发现）

### 2.1 接口

同源、**POST**、`Content-Type: application/json`、**无 token、无验证码**：

| 接口 | 请求体 | 用途 |
|---|---|---|
| `/portalManager/selectLineInfoByDC` | 无 | 线路清单（含线路色） |
| `/portalManager/selectStationInfoByDC` | `{"lineId":"00"}` | 车站清单（含经纬度、地址） |
| `/portalManager/selectDeviceInfoByDC` | `{"line_id":"00","station_id":"0000","device_id":"00"}` | **设施清单** |
| `/portalManager/selectTrainTimeTableInfoByDC` | `{"line_id":..,"trip_drct_cd":"00","stat_station_nme":..}` | 首末班车 |

响应统一为 `{ success, message, code, result: [...] }`。

### 2.2 设施记录的字段与样例

`selectDeviceInfoByDC` 的 `result` 是**扁平数组**，每站每设施一行：

```json
{"lineId":"02","stationId":"0217","stationName":"金融中心","deviceId":"03",
 "deviceDesc":"卫生间","deviceLocationDesc":"站厅层  无;站台层  开往桃仙机场方向车尾位置"}
```

- `deviceId` / `deviceDesc`：设施类别
- `deviceLocationDesc`：**楼层 + 相对位置**，多处以 `;` 分隔

### 2.3 设施类别（全套 9 类）

| deviceId | deviceDesc | 有有效位置文字的站数 |
|---|---|---|
| 01 | 乘客服务中心 | 159 / 159 |
| 02 | 自动售票机 | 159 / 159 |
| 03 | 卫生间 | 159 / 159 |
| 04 | 无障碍卫生间 | 159 / 159 |
| 05 | 母婴室 | 67 / 159 |
| 06 | 无障碍电梯 | 159 / 159 |
| 07 | 自动扶梯（上行） | 159 / 159 |
| 08 | 自动扶梯（下行） | 140 / 159 |
| 09 | 盛京通网点 | 14 / 159 |

注意：官网**没有** AED、没有"直梯"这一叫法（直梯并入"无障碍电梯"）。

中街

甘官（3 号线）
  卫生间           站厅层 站厅A、D口附近 ; 站台层 站台开往李达方向尾端

可归纳的文案特征：

- **楼层词**：`地面层 / 地面-站厅 / 站厅层 / 地下一层 / 站厅-站台 / 站台层 / 站厅层换乘通道`
- **方位词**：`附近 / 位置附近 / 中部 / 两端 / 车头位置 / 车尾位置 / 尾端`，以及`付费区内`
- **站台层带行车方向**：`开往桃仙机场方向车尾位置` —— 本项目已有 `loop-direction.js`
  与"报站目的地"机制，语义上对得上
- **自由文本**：同一含义有多种写法（`附近` / `位置附近`；`厅A、D口` / `站厅A、D口`），
  不宜强行结构化，按原文展示更稳

### 2.5 渲染端已做的清洗（照抄口径）

- 过滤掉 `deviceLocationDesc` 为空或等于 `"无"` 的条目；
- 按 `deviceId` 升序；
- 每条按 `;` 拆行显示；
- 含「暂停」字样的整段隐藏；
- 去掉「（投入使用）」字样；
- 图标取 `/wwmhm/icons//station_device_{deviceId}.svg`（`deviceId=9` 为 `.png`）。

### 2.6 覆盖度（全量实测，非抽样）

- 运营车站 **159** 座（线路：1、2、3、4、9、10 号线）；
- 设施记录 **1431** 条 = 159 × 9，**每站固定 9 条**；
- **设施文字覆盖率 159 / 159**（每站至少含乘客服务中心、自动售票机、卫生间、
  无障碍卫生间、无障碍电梯的文字）；
- **层级图覆盖率 159 / 159**。

## 三、沈阳：副产品（接口里还有这些）

- **每站经纬度**：`selectStationInfoByDC` 的 `onlineX`（经度）/ `onlineY`（纬度），
  十进制度字符串。例：沈阳北站 `123.435951, 41.817299`。
  注意 **3 号线部分站（凌空—方家栏段）为 `"0","0"`**，不可直接使用。
- **每站文字地址**：同接口的 `location`，形如`位于中街路与朝阳街交汇处`
  —— 即本项目 `stacard/data.js` 里 `location` 字段的来源，两处应保持一致。
- **线路色**：`selectLineInfoByDC` 的 `lineColor`（1号线 `#cf3517`、2号线 `#ee782d`、
  3号线 `#e668a0`、4号线 `#6f3d94`、9号线 `#008dd0`、10号线 `#80b72e`）。
- 官网**页面上不展示坐标**，坐标只存在于接口响应里。

## 四、沈阳：车站层级图（本项目已在用）

- 本项目已热链官网层级图，挂在「车站信息」页签；后与设施位置**合并为同一个「车站设施」板块**
  （层级图是该板块的第一个条目、默认展开，见 7.1）。
- 图片地址：移动版 `/wwmhm/icons//czcjt/{官网编号}.png`（`icons` 与 `czcjt` 之间
  的双斜杠是官网自身写法，不可"修正"）；桌面版为单斜杠 `/ckfw/icons/czcjt/{id}.png`。
- 图片体积 **107 KB ~ 519 KB / 站**，159 站合计 **约 30 MB 量级**。
- **图上没有中文设施名**，只有设施图标 + 右侧中英文图例（乘客服务中心 / 自动售票 /
  自动扶梯 / 楼梯 / 出口 / 无障碍电梯 / 卫生间 / 无障碍卫生间 / 母婴室）。
  → 所以层级图**不能替代**结构化设施数据：它能"看"，不能"查"。

## 五、沈阳：ID 映射（已有，不必新建）

- 官网编号 = **2 位线路号 + 2 位站序**，站序**步长为 2**，且是**线路内序号**，
  与全网红线无关；线路内还存在跳号（如 2 号线 `0271` 之后直接跳 `0203`），
  因此**不能靠"上一站 +2"盲推**。
- 本项目 `data_timetable.js` 的 `SYMTC_OFFICIAL_STATION_ID_RULES` 已覆盖
  1 / 2 / 3 / 4 / 9 / 10 号线的映射规则，并被层级图卡片实际使用 —— 设施数据可**复用同一套**。
- 有轨电车、国铁、未纳入官网编号体系的在建站没有官网编号，按「无数据不渲染」处理。

## 六、与上游 CentralGo 的对照

上游的设施模型是**独立数组**，字段为
`{ name{zh,en}, type, source, location{zh}, device_location }`，且**只有文字方位、没有坐标**
（坐标只挂在出入口的 `geo` 上，`facilities` 不参与地图落点）。

| 官网 deviceDesc | 可对到上游的 type |
|---|---|
| 卫生间 | `toilet` |
| 无障碍卫生间 | `accessible_toilet` |
| 母婴室 | `nursing_room` |
| 无障碍电梯 | `elevator` |
| 自动扶梯（上行 / 下行） | 上游把扶梯放在**出入口**的 `accessibility.escalator` 上，而非 `facilities` |
| 乘客服务中心 / 自动售票机 / 盛京通网点 | 上游**无对应**（属运营服务，非"设施"） |

**结论**：若将来要与上游对齐，采用 `facilities[]` + `{name, type, location}` 的形状即可；
但**上游的口径比官网窄**（没有乘客服务中心、售票机、盛京通网点），本项目不必削足适履 ——
按官网 9 类如实呈现更完整，同时保留 `type` 字段以便日后映射。

## 七、落地路径（沈阳已于 2026-10-03 实施）

1. **离线抓取**：开发阶段跑一次脚本，POST 上面 2 个接口（车站 + 设施），
   落成 `city/shenyang/data_facilities.js`（静态常量，与 `data_timetable.js` 同风格）。
2. **ID 映射**：复用 `SYMTC_OFFICIAL_STATION_ID_RULES` 推导官网编号 → 本地车站 ID。
3. **渲染**：仿 `shenyang_service_info.js` 里「出入口」那一行的做法，在「车站信息」
   页签增加一块设施列表；图标用 CGoUI 内置图标（不新增热链依赖）。
4. **清洗**：照 2.5 的口径过滤 `"无"`、去「（投入使用）」、隐藏含「暂停」的段。

**不建议做的事**：

- 不要把层级图下载进仓库（约 30 MB）；
- 不要把设施文字"结构化"成枚举（原文是自由文本，强转会失真）；
- 不要试图从官网取出入口坐标 —— 官网没有。

### 7.1 实施记录（沈阳，2026-10-03）

已按上述路径落地，实际口径与调研略有出入，记录如下：

- **抓取脚本**：`drunk/tools/facilities/fetch_shenyang_facilities.js`（Node，零依赖，开发期工具，
  不进运行时）。实测 `selectDeviceInfoByDC` 传 `line_id:"00"` 可**一次**返回全部 1431 条，
  不必按线取；重跑该脚本即刷新数据。
- **落盘数据**：`city/shenyang/data_facilities.js`（约 170 KB 静态常量，由脚本生成，勿手工编辑）。
  结构为 `本地车站 ID → [{ type, location: [...] }]`：`type` 是归一化类别（展示名与图标
  放在渲染模块里，数据层不重复存）；`location` 是按 `;` 拆段并清洗后的位置原文，
  **多线换乘站**的每段升级为 `{ line, text }`——换乘站的「站厅层 / 站台层」指的是本线那一层，
  不标线名会把两条线的位置混在一起；单线站无歧义，仍存纯字符串以免每段都冗余一份 line。
- **映射核对**：本地 **144** 座车站 ↔ 官网 **159** 个编号，差额 15 即双线换乘站各占 2 个编号；
  脚本会打印「官网有数据但本地未映射」的编号，本次为空。各类别覆盖站数：乘客服务中心 /
  自动售票机 / 卫生间 / 无障碍卫生间 / 无障碍电梯 / 扶梯（上行）各 144，扶梯（下行）128，
  母婴室 65，盛京通网点 14。
- **清洗**：在 2.5 的口径上补了一条「整段以『无』结尾也丢弃」（如 `站厅层  无`，表示该层
  没有此设施），共丢弃 374 段；换乘站跨线合并后按位置文本去重。
- **渲染**：`city/shenyang/modules/shenyang_facilities.js`，注册于 `station-info` 页签
  （order 6，排在「报站指引」(1) 与「站名题写者」(7) 之间）。版式：小节标题「车站设施」
  之下，一行一个条目，左侧「CGoUI 图标 + 名称」、右侧是位置条数与「详情 / 收起」开合
  按钮（结构与「站名题写者」一致，复用同一套交互约定），点开后逐段展示位置原文，
  换乘站每段前标注所属线路名（线名从 `linesData` 解析，不写死在数据里）；
  末尾一行小字注明数据来源。图标均取自 `core/cgo-ui.js` 内置（`counter / payment /
  toilet / a11ytoilet / baby / elevator / escup / escdown / card`），未新增热链依赖。
  样式在 `city/shenyang/style.css`。
- **层级图并入同一板块**（原独立模块 `modules/shenyang_level_map.js` 已删除）：层级图成为
  板块的第一个条目「车站层级图」，**默认展开**（可点「收起」）；官网图是白底 PNG，故配色
  固定浅色、不随亮暗主题切换，也不再加外层阴影与标题条。加载失败即清空该块。这样两个
  语义相近的板块不再在一个页签里并列。
- **跨线去重与楼层排序**（人工核对官网两线记录后确定，规则落在抓取脚本里）：
  - **同一处只算一条**：描述只点出入口时按出入口集合判同一处（站厅、地面出入口是两线
    共用的）；另有两条按站登记的已知事实——**青年大街** 1、2 号线共用站厅，凡非站台层的
    描述（站厅层 / 地面-站厅 / 站厅-站台…）两线指的都是同一处，判重时忽略括注、但**保留
    括注**（两部落客不同 2 号线站台的换乘电梯正靠括注区分）、**太原街**两条提及
    「换乘通道」的描述是同一处。合并后的段落不再挂 `line`（它本就不属于某一条线），
    渲染时也就不标线名。
  - **站台层不参与合并**——那是各线自己的站台，文字相同也保留两条。
  - **按楼层排序**：地面层 → 地面-站厅 → 地下一层 → 站厅层 → 站厅-站台 → 设备层 →
    站台层；同层内保持官网原序。
- **未做**：长春、哈尔滨未实施；沈阳出入口官网无数据，本轮**挂起**（见第九节第 4 条）。

来源：大连公共交通建设投资集团官网「站点查询」（H5 微站，页面标题「微出行」）。
入口页 `https://www.dltransgrp.com/hb-air-web/html/wxgo/stationList.jsp`，
详情页 `.../wxgo/stationDetail.jsp?siteId=24`。桌面官网不暴露入口链接，但页面可直接访问。

**接口**（同源、POST、无 token，响应为 `{ result, error_code }`；`siteId` 不存在时返回
HTTP 500 的 HTML 错误页而非 JSON）：

| 接口 | 请求体 | 用途 |
|---|---|---|
| `/hb-air-api/site/getDefaultMetroLine.do` | 空 | **一次返回全部线路与车站**（含设施与经纬度） |
| `/hb-air-api/site/ShowSite.do` | `siteId` | 单站详情（含**出入口**） |
| `/hb-air-api/site/getMetroLine.do` | `startSiteId` | 从某站可达的线路 |

**设施只有 3 个平铺字段**（不是沈阳那种"每站 9 行记录"）：

| 字段 | 含义 | 覆盖度（108 座站） |
|---|---|---|
| `toilet` | 卫生间 | 108 / 108 |
| `rechargeMachine` | 充值机（自动售票） | 82 / 108 |
| `accessibilityElevator` | 无障碍电梯 | 96 / 108 |
| `atm` | 取款机 | 0 / 108（**恒为 null**） |

**没有**母婴室、无障碍卫生间、扶梯、客服中心等独立字段；个别位置文本里会顺带写到
（如姚家的"残疾人卫生间"、大连北站的"罗森便利店旁"）。

位置文案形态（逐字抄录）：

```
联合路    卫生间: 海之韵→大连北站方向车尾
          充值机: 站厅B口附近
          无障碍电梯: 站内:付费区-靠近A口进站闸机位置,站外:A口
姚家      卫生间: 女卫生间、残疾人卫生间：姚家→河口车头方向、男卫生间：河口→姚家车尾方向
龙王塘    卫生间: 付费区内二楼站厅
          无障碍电梯: 站厅非付费区-一楼至2楼站厅，站厅付费区-上下行站台
虎滩新区   卫生间: 站台层端门附近
          无障碍电梯: 站外电梯：C口旁1台，站厅与站台中间位置1台
```

与沈阳同样是"楼层 + 相对位置"的自由文本；站台方位用**行车方向**表达；无障碍电梯另有
一套 `站内:…,站外:…` 的分段写法。

**大连有出入口信息（沈阳没有）**：`ShowSite.do` 的 `siteInfo.siteExitList[]` 每条含

```
siteExitId, exportName（出口字母，如 "A"）,
busLine（"10路、705路、34路、931路、8路"）,
stationBuilding（周边地标，"大连第七十九中学、大连市卫生事业发展中心"）,
commercialBuilding, dynamicNotice, status（"2" = 暂停使用）, statusStr
```

即：有字母、有公交线路、有周边地标、有启用状态；**但没有方位**（不写东/南/西北）、
**没有坐标**。注意聚合接口 `getDefaultMetroLine.do` 里 `siteExitList` **恒为空数组**，
出入口必须**逐站**调 `ShowSite.do`（108 次）。

**其它**：

- **每站都有经纬度**：`siteInfo.longitude / latitude`，108/108 齐全（联合路
  `121.60304, 38.919882`、金石滩 `122.013019, 39.092547`）；详情页的「地图」按钮就是
  拿它跳 `baidumap.jsp?lng=…&lat=…`。**出入口没有坐标。**
- **线网图 H5 不可用**：`https://www.dltransgrp.com/h55/app-h5/metromap/#/?cityId=2102`
  走的是另一套域名 `ecx.dlmetro.com`，需要 `appid` + **RSA 签名**
  （`appid/nonce/timestamp/sequence/random/publicKey`，签名串先 MD5 再 JSEncrypt 加密），
  纯静态项目无法直连；且该图上**没有任何设施信息**，它只做路径规划。
- **CORS 实测结论**：

  ```
  access-control-allow-origin: https://www.dltransgrp.com
  access-control-allow-credentials: true
  ```

  只放行官网自身域名 → **纯静态站不能跨域直连**，与沈阳同样需要离线抓取落盘。
  好在大连只需**一次** `getDefaultMetroLine.do` 就能拿到全部 108 站的设施与经纬度，
  出入口再逐站补（108 次）。

### 8.2.1 实施记录（长春，2026-10-03）

- **源与时效**：长春轨道交通官方公众号推送的《车站设施位置一览》表格图，**2025-04 发布、此后未更新**。
  时效已核实：源图含 1、2、3、4、6、8 号线共 **125 座运营站**；5 号线一期 2026-09-28 才开通；
  7 号线一期 2026-08-26 开通（本城数据 2026-09-14 入库时它已在运营，故既不进未开通表也不进开通时刻表）；
  1 号线南延、3 号线南延在源图发布时尚未运营。**表中没有 5、7 号线不是遗漏。**
- **取数方式（与沈阳、大连不同）**：官方没有可抓取的设施接口，表格图也无法自动解析，故走
  「人工转录 → 脚本生成」：转录件 `drunk/tools/changchun_facilities.transcript.json` 只忠实记录原表
  （列名、格子原文、哪些列未收录），口径全在 `drunk/tools/facilities/gen_changchun_facilities.js`
  （列 → 归一化类型、电梯 / 升降平台归类、站名别名、跨线不合并），产出 `data_facilities.js`。
  **代价**：这是 2025-04 的静态快照，**不会随官网自动刷新**——重跑脚本只重放转录件，不会去抓新数据。
- **列集不统一**：官方每条线路一张表——1/2/4 号线 8 列（含自助照相机）、3 号线 7 列（末列为 AED）、
  6 号线 9 列（另有母婴室位置）、8 号线 5 列。「车内轮椅固定位置」列**未收录**：
  其值是「5号、20号屏蔽门」「车辆中间位置」这类车厢 / 屏蔽门位置，不是站内设施。
- **换乘站的拆段与合并**（这两条经过一轮调整，以本版为准）：
  - **拆段**：官方常把同一设施的多个位置串在一格（「B口安检旁、CD口通道」「A口通道、站厅付费区」），
    按「**每一段都含位置词**」拆成多段；但「A、B口通道」「A1口、B1口」这类**出口字母并列**不拆，
    「换乘通道，站厅层中部」「长影世纪城方向，站厅层西南」这类**对前段的楼层层位补充**也不拆。
  - **合并**：同一处被两条线各写一遍时只留一份、不标线名。判据分三档：
    ① 两条线的**取值集合完全一致**（如解放大路的饮料 / 文创 / 充电宝、福祉大路的饮料）；
    ② 官方自己写明「**同N号线**」——长春站 3 号线的无障碍电梯原文就是「B口，同1号线」；
    ③ **已查证的共用站厅 / 同台换乘站**整站归一合并，登记在生成脚本的 `SHARED_STATIONS`：
       **伪满皇宫**（3、4 号线**同台换乘**，站台为**地下双岛式**；依据见第九节第 6 条）与
       **长春西站**（2、6 号线共用 B1 的**东、西两个乘车大厅**，无障碍电梯设在西大厅、通向站台层）
       ——这两站同类型取「段数最多、其次总字数最多」的那条线的写法。
    ④ **单条人工登记**：两线措辞不同、但主理人确认是同一处的**单条**文案，登记在
       `SAME_PLACE_OVERRIDES`，合并取信息量大的那份——长春站北的饮料售卖机
       （「B口设备门口」／「B口通道」）、福祉大路的充电宝（「D口换乘通道内」／「D口通道」）。
    各线取值不一致时，只把**两线都写到的同一条文案**合并成一条，线内独有的仍标线名。
- **无障碍电梯 / 升降平台**：官方合并成一列，但官方原文本就分行书写（如吉林大路「D口」+
  「CE换乘通道(升降平台)」两行），故**按段落归类**：提到升降平台的归升降平台、其余归无障碍电梯，
  共 3 处（吉林大路、解放桥、卫星广场）。
- **渲染**：`city/changchun/modules/changchun_facilities.js`，注册于 `station-info`（order 6），
  与沈阳、大连同用共享层 `city/shenyang/shared/facilities.js`。饮料 / 文创自动售卖机与充电宝
  在 CGoUI 暂无专用图标，按现有图标择近降级为 `info`；其余用 `toilet` / `baby` / `elevator` /
  `a11yplatform` / `aed` / `camera`。**AED 一行用共享层的 `tone` 强调位**（`tone: "alert"`，
  样式在 `shared/facilities.css`）：图标与开合按钮文字转红，急救设备一眼可辨。
- **顺带补的**：`city/changchun/staname.csv`（该城原本没有此文件）收录 3 条已查证的站名别名
  ——`职业学院` → 职业技术大学（2026-05 官方更名公告）、`市委市政府` → 市政府、
  `硅谷广场` → 硅谷广场(吉大中心校区)；并在 `changchun.js` 的 `dataFiles` 里声明了 `stanameCsvUrl`。
- **原图不清的 3 处已核对补齐**（2026-10-03，主理人核原图）：1 号线长春站北的卫生间 =
  「站厅层进站口旁」（先前字形近似读作「站厅层医站口旁」，实为误读）；4 号线天工路的卫生间 =

### 8.3 跨城统一数据结构建议

三市字段形态差别较大（沈阳是"每站 9 行记录 + 设施名/位置两字段"，大连是"每站 3 个
平铺字段"，长春是"每条线路一张表、列集 5~9 列不等"），若将来多城都做，建议**在数据层统一成一个与来源无关的形状**，各城只写映射：

```
stationId                      // 本项目的车站 ID（不是官网编号）
facilities: [
  { type,                      // 归一化类别：toilet | accessible_toilet | elevator |
                               //   escalator | nursing_room | customer_service |
                               //   ticket_machine | service_center | atm
    name,                      // 展示名，保留来源原文（"充值机" / "自动售票机"）
    location: [ "…", "…" ],    // 直接放来源原文，按 ; 或 , 拆好，不强行结构化
    source }                   // 来源标识（便于署名与排障）
]
exits: [                       // 沈阳、大连均已实施；没有的城市留空数组
  { name,                      // 出口字母
    lines: [],                 // 所属线路（沈阳有；大连官网不提供）
    buses: [], landmarks: [],  // 公交与周边地标（目前仅大连有）
    closed: false }            // closed 为 true 即官网标注「暂停使用」
]
```

> 2026-10-03 补充：**设施里「以某个出入口为起终点的扶梯 / 电梯」已从 `facilities` 搬到对应出口下**
> （上游把扶梯放在出入口的 `accessibility.escalator` 上、而非 `facilities`，本项目这次与该口径一致）。
> 判据是**位置文本前缀**（沈阳 `地面-站厅 / 地面层 / 站厅层 / 地下一层 / 站厅-地面`、大连 `站外`），
> 不是「文本里出现出口编号」——「站厅-站台 A出入口附近」同样提到出口编号，但它是站内电梯、留在设施板块。
> 机制与配置见 `city/shenyang/shared/README.md` 的 `exit-vertical.js` 条目。

理由：`location` 是自由文本（"站厅层 站厅中部位置" / "海之韵→大连北站方向车尾"），
强转成枚举会失真；真正需要归一的只有 `type`。这样沈阳的 9 类与大连的 3 类可以并存，
将来对上上游 CentralGo 的 `facilities[].type` 也只改映射表。

## 九、未决问题

1. **跨域**：**大连已实测** —— `hb-air-api` 的 `access-control-allow-origin` 只放行
   `https://www.dltransgrp.com`，纯静态站无法直连，必须走离线抓取；沈阳侧未实测，
   但接口形态相同，按同样口径准备即可。
2. **抓取频率与礼貌**：沈阳 159 站、大连 108 站，各抓一次即可，无需轮询；落盘后与
   官网可能长期不一致，需要约定一个"手动更新"的节奏。
3. **署名与合规**：数据分别来自沈阳地铁官网与大连公共交通建设投资集团官网，
   展示时应按城市注明来源；不可声称"官方数据"，自行采集的结论须标注待核验。
4. **出入口**：大连官网那批（字母 + 公交线路 + 周边地标 + 启用状态）可以先用起来 ——
   比沈阳的纯字母强得多，且本来就不含坐标，正好落在"文字方位"这一档。若要做到
   **落图**，仍需坐标，候选来源是 OSM（`railway=subway_entrance`，ODbL 开放、
   自带经纬度，上游亦以其为主要来源），但**沈阳 / 大连两市的 OSM 覆盖度尚未核查**。
   → **部分已决（2026-10-03）**：大连已按"文字档"实施（100 站 / 260 条，见 8.1.1），
     本轮不做落图；**沈阳挂起** —— 官网无出入口数据，"暂停使用"以外的信息来源只剩设施
     文案里散落的字母（既不完整、也无公交与地标，不足以单独成表），待评估 OSM / 高德
     能否补到字母与坐标后再定。
5. **本项目的定位取舍**：沈阳一侧现有重心是"文化"（题字、文化墙、报站目的地），
   大连一侧是运营数据（时刻表、票务），设施属纯功能信息，是否纳入、以及先在哪个
   城市做，需与城市主理人的编辑方针一致。
   → **已决（2026-10-03）**：沈阳、大连均已落地（见 7.1、8.1.1）。
6. **换乘站的车站结构（决定设施要不要跨线合并）**：已查证两站——
   - **伪满皇宫（3、4 号线）**：**同台换乘**，站台为**地下双岛式**。
     依据：城市晚报 2021「伪满皇宫站也将实现 3、4 号线的同台换乘」（3 号线东延线报道）；
     本地宝 4 号线站表把该站站台形式记为「地下双岛式」；3 号线纪实视频文案亦称
     「伪满皇宫站可与四号线同台换乘，站台为地下双岛式」。
   - **长春西站（2、6 号线）**：**共用站厅**——车站形式为岛式二层车站，地下一层为
     **东、西两个乘车大厅**，两个大厅在**西大厅**设有无障碍电梯通向站台层；地下二层为 2 号线站台。
     （两线站点均位于国铁长春西站综合换乘中心内。）
   其余换乘站（解放大路、长春站、长春站北、解放桥、福祉大路、卫星广场）**未查证到共用站厅**，
   是按「取值集合是否一致」机械判定的（见 8.2.1）；若要继续收紧，应逐站查结构再登记进
   `SHARED_STATIONS`，不要凭文案相似度猜。
